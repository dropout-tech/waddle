## 二、讓註冊確認信／忘記密碼信寄得出去（C11）— 已查證：目前**沒設定**

為什麼：Huddle 的登入服務（Supabase）預設的寄信功能只會寄給專案成員。目前設定是「註冊後要點確認信才能登入」，所以**一般人用 email 註冊會收不到確認信、無法完成註冊；忘記密碼也收不到信**。App Store 審查員如果用 email 註冊，也會卡住。
過去 7 天紀錄裡沒有人用 email 註冊或重設密碼，所以目前還沒有真的客人被擋到。

做法：用 Resend 寄信，寄件網域 lazy72.com。分三段，**A、B 你本人做；C 也是你本人貼金鑰**。

### A. Resend 開帳號、加網域
1. 到 resend.com 用你個人帳號（建議 lazydragon0247@gmail.com，跟 Huddle 其他服務一致；不要用公司 dropout 的帳號）註冊。免費方案：每月 3,000 封、每天 100 封，夠用。
2. 左側 Domains → Add Domain → 輸入 `lazy72.com`，地區選 Tokyo（ap-northeast-1，離台灣近）。
3. Resend 會列出 3～4 筆 DNS 記錄（名稱大致是 `resend._domainkey`、`send` 的 MX 與 TXT，可能還有 `_dmarc`）。**這一頁先別關。**

### B. 把記錄加到 Cloudflare
1. 登入 Cloudflare（lazydragon0247 帳號）→ lazy72.com → DNS → Records。
2. 照 Resend 頁面的值一筆一筆 Add record（類型、名稱、內容照抄；Proxy 一律灰色「DNS only」）。若 Resend 出現「Sign in to Cloudflare／Auto configure」按鈕，也可以按它自動加。
3. **不要動**現有的 `lazy72.com` MX（Gandi）和根網域那筆 `v=spf1 include:_mailcust.gandi.net ?all`：那是你 lazy72.com 信箱收信用的，Resend 的記錄掛在 `send.` 底下，兩者不衝突。
4. 回 Resend 按 Verify，幾分鐘到幾小時會變綠色 Verified。
5. Resend 左側 API Keys → Create API Key（權限選 Sending access、網域選 lazy72.com）→ 複製（只會顯示一次）。

### C. 填進 Supabase
1. supabase.com → 專案 penguinflow（jnikcndiexjojgvicohf）→ Authentication → Emails → SMTP Settings → 打開 Enable Custom SMTP。
2. 填：
   - Sender email：`noreply@lazy72.com`
   - Sender name：`Huddle`
   - Host：`smtp.resend.com`
   - Port：`465`
   - Username：`resend`
   - Password：貼上剛剛的 Resend API Key
3. Save。
4. 告訴工程端「SMTP 設好了」→ 工程端會用唯讀方式讀回設定確認，再請你用一個沒註冊過的信箱（例如你另一個 Gmail）在 `https://huddle.lazy72.com/signup` 註冊，看收不收得到確認信、會不會進垃圾信。

## 三、Apple「隱藏我的電子郵件」使用者收信（C6）— 第二段做完再做

為什麼：用 Apple 登入、又選「隱藏我的電子郵件」的人，Huddle 看到的是一個 @privaterelay.appleid.com 的轉信地址。Apple 只轉「登記過的寄件來源」寄來的信，沒登記的信直接丟掉。
影響有多大：目前 Huddle 只有註冊確認信和忘記密碼信，Apple 登入的人用不到這兩封，所以**現在不急**；之後如果要寄通知信、帳單信，就一定要做。

步驟（你本人在 Apple 開發者後台做）：
1. developer.apple.com → Account → Certificates, Identifiers & Profiles。
2. 左側 Services → 找「Sign in with Apple for Email Communication」→ Configure。
3. Email Sources 按 ＋：
   - Domains：加 `lazy72.com`
   - Email Addresses：加 `noreply@lazy72.com`
4. 按 Register。Apple 會檢查這個網域的 SPF；狀態出現綠勾才算數，紅色就截圖給工程端看。

要加的 DNS：第二段 Resend 那幾筆加完就夠了，**不用另外加**。
（工程端信心約七成：Apple 檢查的是寄件網域的 SPF，Resend 的 SPF 掛在 `send.lazy72.com`。如果 Apple 顯示 lazy72.com 的 SPF 沒過，再把 `send.lazy72.com` 也加進 Domains，不要去改根網域的 SPF。）

## 四、Google 品牌驗證：讓授權畫面顯示「Huddle」（C7）— 第一段第 4 項通過後做

為什麼兩件事：
- 授權畫面現在顯示網址而不是「Huddle」→ 要做「品牌驗證」。
- 目前專案在「測試模式」→ Google 日曆的授權**大約 7 天就失效**，使用者要重連；而且只有登記過的 2 位測試者能用。改成「正式發佈」以後就不會 7 天失效。日曆權限屬「敏感權限」，正式發佈後在審核通過前，使用者會先看到「Google 尚未驗證這個應用程式」的警告頁（可以按進階繼續），最多 100 人。

### 你要準備／確認的（工程端已確認的打勾）
- ✅ 首頁：`https://huddle.lazy72.com/about`（公開、介紹 Huddle、頁尾有「隱私說明」「服務條款」連結，瀏覽器實測確認）
- ✅ 隱私權政策：`https://huddle.lazy72.com/privacy`（英文：`/en/privacy`）— 已寫明 Google 日曆唯讀、事件不存伺服器、遵守 Google API「有限使用」規定
- ✅ 服務條款：`https://huddle.lazy72.com/terms`（英文：`/en/terms`）
- ⬜ App 標誌：120×120 的 PNG（企鵝頭像），工程端可幫你從現有圖檔裁一張
- ⬜ 支援信箱：建議用 lazydragon0247@gmail.com（之後也可以改）
- ⬜ 一支示範影片（腳本見下），上傳 YouTube 設成「不公開」

### 步驟（Google Cloud，你的個人帳號，專案「Huddle Calendar」）
1. **先驗證網域所有權**：開 search.google.com/search-console → 新增資源 → 選「網域」→ 輸入 `lazy72.com` → 它給你一串 `google-site-verification=…` 的 TXT。到 Cloudflare 的 lazy72.com DNS 加一筆 TXT（名稱 `@`，內容貼上），回 Search Console 按驗證。（這筆不會影響收信。）
2. Google Cloud Console → 左上切到「Huddle Calendar」→ Google Auth Platform → **Branding**：
   - App name：`Huddle`
   - User support email：上面那個信箱
   - App logo：上傳那張 120×120
   - Application home page：`https://huddle.lazy72.com/about`
   - Privacy policy：`https://huddle.lazy72.com/en/privacy`
   - Terms of service：`https://huddle.lazy72.com/en/terms`
   - Authorized domains：`lazy72.com`（舊的 zeabur.app 如果在清單裡可以先留著）
   - Developer contact：你的信箱 → Save
3. **Data Access**：確認只有一個權限 `.../auth/calendar.events.owned.readonly`。用途說明（Justification）貼下面英文那段。
4. **Audience** → Publishing status 按「Publish app」（從 Testing 改成 In production）。
5. **Verification Center** → 送出驗證，填影片的 YouTube 網址。
6. 之後 Google 會寄信到開發者信箱問問題，**轉給工程端一起回**，不要自己先回。

### 權限用途說明（貼進 Justification）
> Huddle is a personal planner (tasks, calendar, focus timer, notes). With the user's explicit opt-in on the Settings › Google Calendar page, Huddle reads events from the user's own primary Google Calendar (read-only, calendar.events.owned.readonly) and displays them on the Huddle calendar so the user sees meetings next to their tasks. Event contents are fetched on demand and are not stored on our servers; only an encrypted refresh token is kept. If the user also enables "avoid my Google meetings when partners find a time" (on by default, can be turned off), a share partner who looks for a common free slot sees only busy start/end times — never titles, locations, attendees or links. Users can disconnect at any time, which deletes the stored token. We do not use the data for ads, do not sell it, and do not use it to train AI models. Huddle's use of Google user data complies with the Google API Services User Data Policy, including the Limited Use requirements.
